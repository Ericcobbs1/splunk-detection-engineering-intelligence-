# DEI Splunk UI Toolkit Migration Plan

## Objective

Move Detection Engineering Intelligence from a Simple XML + jQuery presentation layer to a Splunk UI Toolkit (SUIT) React application shell without rewriting or destabilizing the Python recommendation engine, REST handlers, telemetry discovery logic, or Splunk app packaging.

## Current state

DEI currently has:

- Python REST handlers and recommendation engine.
- A data-driven detection catalog.
- Runtime telemetry normalization and field readiness logic.
- A Simple XML `command_center` view.
- `command_center.js` for Splunk REST/search interaction.
- `command_center.css` for custom presentation.

This is a working backend and should remain the system of record during frontend migration.

## Target state

```text
Splunk Enterprise / Splunk Cloud
        |
        +-- DEI Python / REST backend
        |     +-- health
        |     +-- telemetry discovery support
        |     +-- recommendations
        |     +-- future validation/lifecycle services
        |
        +-- DEI SUIT React application
              +-- AppShell
              +-- Command Center
              +-- Detection Advisor
              +-- Coverage
              +-- Detection Engineering
              +-- Data Intelligence
              +-- Settings
```

## Supported migration approach

Follow Splunk's documented approach for adding SUIT to an existing Splunk Web Framework app:

1. Set up the supported Node/Yarn environment for the selected SUIT release.
2. Use `npx @splunk/create` to generate a React component/monorepo.
3. Use `@splunk/create` to generate the Splunk UI app shell that uses the component.
4. Link the generated app shell to the existing DEI Splunk app during development.
5. Move UI workflows into React incrementally while preserving existing backend endpoints.

Reference:
https://dev.splunk.com/enterprise/docs/developapps/createapps/buildapps/adduicomponent

Do not hand-author a substitute scaffold when the supported generator can establish package compatibility and build conventions.

## Migration phases

### Phase 0 - Portfolio foundation

Status: first implementation target.

Deliverables:

- Portfolio UI standard.
- Component contract.
- Semantic state vocabulary.
- Token alias contract.
- Review gate for future UI PRs.

### Phase 1 - Generate SUIT shell

Deliverables:

- Supported `@splunk/create` workspace.
- DEI React app package.
- Shared portfolio component package.
- Development link into the existing Splunk app.
- Build/start scripts generated by Splunk tooling.
- No backend behavior changes.

Acceptance criteria:

- Generated app renders inside the existing DEI Splunk app.
- Health endpoint can be called from the React shell.
- Existing Simple XML command center remains available as a fallback during migration.

### Phase 2 - Shared portfolio primitives

Implement reusable components from `PORTFOLIO_COMPONENT_CONTRACT.json` using Splunk UI components and theme tokens:

- AppShell
- PageHeader
- MetricCard
- StatusBadge
- SeverityBadge
- HealthBanner
- EmptyState
- ErrorState
- LoadingState

Acceptance criteria:

- No app-specific colors embedded in primitive components.
- Keyboard/focus behavior is inherited from or aligned with Splunk UI components.
- Dark/light theme behavior is tested where supported.

### Phase 3 - DEI Command Center

Rebuild the current landing page using shared primitives.

Sections:

1. Page header and API/dependency health.
2. Environment discovery state.
3. Executive detection metrics.
4. Detection portfolio readiness.
5. Telemetry/coverage profile.
6. Prioritized recommendations.

New shared components:

- DetectionCard
- CoveragePanel
- EvidenceDrawer

Acceptance criteria:

- Recommendation API payload and semantics remain unchanged.
- Ready/partial/field-gap/unverified states are visually distinct and text-labeled.
- MITRE technique context is available without dominating the primary workflow.
- Detailed field/source evidence opens progressively rather than filling the landing page.

### Phase 4 - Detection Advisor

Create a dedicated recommendation workflow rather than limiting recommendations to the overview.

Capabilities:

- filter by readiness, severity, pack/domain, and telemetry source
- inspect missing telemetry
- inspect missing/unverified fields
- view source normalization evidence
- view MITRE mapping
- open implementation workflow

### Phase 5 - Coverage and Data Intelligence

Create dedicated pages for:

- source coverage
- TA/parser state
- CIM state where applicable
- field readiness
- data quality
- last-seen/activity
- detection coverage by domain and MITRE

The UI must distinguish native vendor/TA coverage from CIM coverage. CIM is evidence, not a fabricated requirement for every source.

### Phase 6 - Detection Engineering workflow

Add lifecycle surfaces after the recommendation and telemetry foundation is stable:

- detection library
- candidate design
- validation
- tuning
- promotion
- lifecycle state
- optional Enterprise Security integration

## Backend contract rules

Frontend migration must not encode Splunk SPL or source-specific business logic directly into presentation components when that logic belongs in the backend.

Preferred layering:

```text
React component
  -> typed client/service
    -> DEI REST endpoint
      -> recommendation/telemetry domain logic
        -> Splunk search/runtime
```

Temporary direct search calls are allowed only when no stable backend endpoint exists and should be tracked for later consolidation.

## Portfolio package strategy

The generated SUIT workspace should eventually contain at least two logical packages:

```text
packages/
  portfolio-ui/       reusable Splunk-native primitives
  dei-app/            DEI application shell and pages
```

Future apps should consume `portfolio-ui` instead of copying DEI components.

Potential later packages:

```text
portfolio-security-ui/   security-specific cards/badges/evidence components
portfolio-splunk-client/ shared Splunk REST/search client helpers
```

Do not create these packages until there are at least two real consumers or a clear cross-app need.

## Design constraints

- Prefer `@splunk/react-ui` components.
- Prefer `@splunk/themes` tokens.
- Prefer `@splunk/react-icons`.
- Prefer Splunk visualizations instead of custom chart implementations.
- Use UDF for dashboard-first pages.
- Do not ship custom fonts.
- Do not make dark mode the only usable mode unless the product requirement explicitly demands it.
- Preserve Splunk Cloud/AppInspect packaging constraints.
- Increment release version/build when static assets change for a release.

## PR strategy

Keep migration PRs small and reversible:

1. portfolio standard/contract
2. generated SUIT workspace
3. shared primitives
4. DEI command center React page
5. recommendation evidence/drilldowns
6. dedicated workflow pages
7. retire legacy Simple XML only after feature parity and runtime validation

## Exit criteria for legacy command center

The Simple XML command center may be retired only when:

- React command center reaches feature parity.
- REST/search behavior is validated in Splunk Enterprise.
- required Splunk Cloud/AppInspect checks pass.
- error/loading/empty states are verified.
- no critical workflow depends on the legacy jQuery extension.
- rollback instructions exist for the release that removes it.
